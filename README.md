# ChatterBox

A real-time, WhatsApp-style chat app you run entirely on your own machine — free and open-source end to end, no paid services, no API keys, no cloud database.

## Stack (100% free/open-source)

| Layer | Tech | Why |
|---|---|---|
| Frontend | React 18 + Vite | Fast dev server, no paid tooling |
| Realtime | Socket.IO | WebSocket messaging with polling fallback |
| Backend | Node.js + Express | Simple REST API for auth/history |
| Database | Node's built-in `node:sqlite` | Zero install — no native build tools, no separate DB server, just a file on disk |
| Auth | JWT + bcryptjs | Stateless auth, password hashing (pure JS, no native deps) |
| Icons | lucide-react (MIT) | |

Nothing here requires a credit card, an account, or an internet connection once installed.

## Features

- Username/password accounts (JWT sessions)
- 1:1 direct messages **and** group chats
- Real-time delivery via Socket.IO
- Typing indicators
- Online/offline presence + "last seen"
- Read receipts (double blue tick, WhatsApp-style)
- Unread message badges
- Emoji picker
- **6 switchable themes**: Classic (WhatsApp green), Midnight (dark/OLED), Aurora (glass/gradient), Retro (Y2K messenger blue), Neon (cyberpunk), Sunset (warm gradient) — picked from the palette icon, persisted per-browser
- Responsive layout (mobile-friendly)

## Project layout

```
whatsapp-clone/
  server/     Express + Socket.IO + SQLite backend
  client/     React + Vite frontend
```

## Running it

You need [Node.js](https://nodejs.org) 22.5+ (24.x recommended — this project uses Node's built-in SQLite module). Check with `node -v`.

**1. Start the backend** (in one terminal):
```bash
cd server
npm install
npm run dev
```
Runs on http://localhost:4000. A SQLite file is created at `server/data/chatterbox.db` on first run.

**2. Start the frontend** (in a second terminal):
```bash
cd client
npm install
npm run dev
```
Runs on http://localhost:5173 — open that in your browser.

**3. Try it out**: register two different accounts in two browser windows (or one normal + one incognito), start a chat between them, and send messages back and forth to see real-time delivery, typing indicators, and read receipts.

A few demo accounts already exist from development testing (username / password): `alice` / `pass123`, `bob` / `pass123`, `carol` / `pass123`. Delete `server/data/chatterbox.db` any time to start with a clean database.

## Configuration (optional)

The server reads optional environment variables (all have sane local defaults, nothing required):

- `PORT` — server port (default `4000`)
- `JWT_SECRET` — signing secret for auth tokens (default is a dev placeholder — set your own if you ever deploy this beyond your machine)
- `CLIENT_ORIGIN` — allowed CORS origin (default `http://localhost:5173`)

In development, the client talks to the backend through Vite's dev proxy (`/api` and `/socket.io` → `http://localhost:4000`, configured in `client/vite.config.js`) so both run on their own ports with no CORS setup needed. In production the server serves the built client itself, so they share one origin automatically. Set `VITE_API_URL` only if you ever split the API onto a separate domain from the frontend.

## Deploying to Render (free, no card required)

Render's free tier needs no payment method at all, and reuses the exact same [Dockerfile](Dockerfile) already in this repo — one image builds the React app and bundles it into the Node server, so the server serves the API, Socket.IO, and the frontend all from one origin.

**The one real tradeoff:** Render's free tier has no persistent disk. The SQLite file lives inside the container's ephemeral filesystem, so it can be wiped on a redeploy or an underlying host restart. Fine for a personal/demo chat app; if you outgrow that, swap in a free hosted Postgres later (Render, Neon, and Supabase all offer one).

**One-time setup:**

1. Push this project to a GitHub repo (Render deploys from git — see commands below if you haven't done this yet).
2. Sign up at https://render.com with GitHub — no card needed.
3. In the Render dashboard: **New +** → **Blueprint** → pick your repo. Render auto-detects [render.yaml](render.yaml) in this repo and configures the service from it.
4. Before deploying, edit [render.yaml](render.yaml): change `name: chatterbox-changeme` to something unique, and update `CLIENT_ORIGIN` to match — it must equal `https://<your-chosen-name>.onrender.com` so Socket.IO's CORS check accepts your own frontend. `JWT_SECRET` is auto-generated by Render, nothing to do there.
5. Click **Apply** / **Deploy**. Render builds the Dockerfile and gives you a URL — visit `https://<your-name>.onrender.com`.

**Pushing to GitHub** (from inside `whatsapp-clone/`, if you haven't already):
```bash
git init
git add .
git commit -m "Initial commit"
```
Then create an empty repo at https://github.com/new (don't initialize it with a README), and:
```bash
git remote add origin https://github.com/<your-username>/<repo-name>.git
git branch -M main
git push -u origin main
```

**Redeploying later:** just `git push` — Render auto-deploys on every push to the connected branch.

**Heads up on free-tier behavior:** Render's free web services spin down after ~15 minutes of no traffic and take 30-60 seconds to wake back up on the next request (slower than Fly's near-instant resume, since Render's free tier fully stops the container rather than suspending it). That's the price of not needing a card — acceptable for a personal chat app, just don't expect instant responses after it's been idle.

### Alternative: Fly.io (faster, but needs a card on file)

Fly's free allowance is more generous in practice (persistent volume for your SQLite file that survives redeploys, and near-instant wake from idle instead of Render's 30-60s cold start) — but Fly now requires a payment method on file for every new org before it'll assign machines, even within the free quota. The [fly.toml](fly.toml) in this repo is already set up if you want to switch later:

1. Add a payment method at https://fly.io/dashboard, then `fly auth login`.
2. Pick a globally-unique app name and put it in `fly.toml` (`app = "..."`).
3. `fly volumes create chatterbox_data --region iad --size 1` (match region to `primary_region` in fly.toml).
4. `fly secrets set JWT_SECRET="$(openssl rand -hex 32)" CLIENT_ORIGIN="https://<app>.fly.dev"`
5. `fly deploy`

## Adding another theme

Every theme is just a block of CSS custom properties in [client/src/themes/themes.css](client/src/themes/themes.css) selected by `[data-theme="yourtheme"]`. Add a new block there, then register it in the `THEMES` array in [client/src/context/ThemeContext.jsx](client/src/context/ThemeContext.jsx) so it shows up in the theme switcher.

## Notes

- `npm audit` on the client flags moderate advisories in `vite`/`esbuild` (dev-server-only, not exploitable outside actively browsing to a malicious site while the dev server runs) and `react-router` (open-redirect edge case unrelated to how this app uses it). Both are dev-time-only concerns for a localhost app; fixing them requires major version upgrades (Vite 6→8, React Router 6→7) which weren't done here to avoid destabilizing the build — upgrade at your convenience with `npm audit fix --force` in `client/`.
- `node:sqlite` is still marked experimental by Node.js (you'll see a one-line warning in the server console) — it's stable enough for local/personal use here, but if you ever need a hardened production deployment, swap `server/src/db.js` for `better-sqlite3` (same API shape) or Postgres.
